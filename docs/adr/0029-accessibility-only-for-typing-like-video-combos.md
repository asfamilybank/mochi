# 视频控制只在绑了「像打字的组合键」时才请求辅助功能

[ADR-0028](0028-input-monitoring-only-for-typing-like-combos.md) 判断对了「什么时候需要权限」，选错了「要哪项权限」。第二轮实测（2026-10-13，macOS 26.5）：

- 只授予**输入监控**、重新打开 Mochi 之后，WindowServer 查到的状态已是「已授权」，⌥P 在其他应用里**仍然收不到**；Mochi 自己在前台时能收到，那是本地监听，本来就不要权限。全局监听（`NSEvent.addGlobalMonitorForEvents`）对会打出字符的按键的过滤只认**辅助功能**——这正是 Apple 对这个 API 的文档说法。输入监控管的是 `CGEventTap`/IOHID 那一套。
- 输入监控也给不了「点一下允许」：Mochi 第一次被查到时，系统直接把它记成「拒绝」（System Set，没有任何弹框），之后 `CGRequestListenEventAccess()` 只会原样返回拒绝。

所以决定：**只有当视频控制里至少一个触发键是组合键、并且它既不带 ⌃ 也不带 ⌘ 时，才需要辅助功能**——其余（轻按、连按两次、带 ⌃/⌘ 的组合键、Carbon 全局热键、热键传递）一律不要任何按键相关的权限。请求用 `AXIsProcessTrustedWithOptions`（系统弹出指向系统设置的框）；状态用 `AXIsProcessTrusted()`，它分不出「没问过」和「拒绝过」，就借「已自动请求过」的标记来分：没请求过显示「请求权限」，请求过显示「打开系统设置」。ADR-0026 的其余原则不变。

## Considered Options

- **不允许视频控制绑这类组合键**：Mochi 从此不要任何按键权限。没选，因为用户要能用 ⌥ 组合键；代价是视频控制只监听不拦截（[ADR-0020](0020-video-control-listens-never-intercepts.md)），这类按键在别的应用里照常生效——⌥P 会在输入框里打出「π」。
- **改用 `CGEventTap` 的只监听模式、走输入监控**：要和现在的全局监听两套并存（没有权限时 event tap 根本建不起来，轻按就会失效），还要再实测一轮，同样解决不了「在别处打出字符」。

## Consequences

- ADR-0026 记下的升级陷阱照旧适用：ad-hoc 签名升级后辅助功能「开关开着但失效」，要移除再重新添加。
- 放行规则（没有权限时 ⌃⌥P 生效、⌥P/⇧F5 不生效）是实测得来的，系统升级后要重新核对。

## 后续

- 真机验证通过（2026-10-13，macOS 26.5，`/Applications` 下的开发版构建，清掉辅助功能与输入监控两项授权之后）：默认配置进入 Ghost Mode 不请求任何权限、不出现任何提示；把视频控制绑成 ⌥P 后，进入 Ghost Mode 弹一次辅助功能授权框，按钮在请求前后分别是「请求权限」/「打开系统设置」；在系统设置里打开辅助功能后，⌥P 在其他应用里**马上生效，不需要重新打开 Mochi**（轮询发现授权后重装监听这条路是通的）。
